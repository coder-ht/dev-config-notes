# Codex 协作规则

本文件是 `dev-config-notes/codex/` 唯一的规则与经验入口；自定义 Skill 统一放在同级 `skills/`。

## 项目规则与经验

- 根据 Codex 当前工作目录所属的仓库确定项目；工作目录位于仓库子目录时，以仓库根目录为准。仓库为 `cube2-upgrade`、`ghcloud`、`kaihe`、`kaiyun-oa` 或 `baseline` 时，使用本文件对应的项目规则与经验；其他仓库只使用通用章节。
- 跨仓库任务分别确认每个实际操作仓库的工作目录和适用章节。目标仓库最近层级的 `AGENTS.md` 与模块规则也须读取；更具体的规则优先，无法判断冲突时暂停相关操作并询问用户。
- 修改项目代码前核对目标仓库当前源码、配置、接口契约与实际脚本；必要规范缺失或含义不明确时停止相关代码操作并报告。

## 协作与执行

- 需要调用工具时，开始前简要说明目标与范围。普通、范围明确且可回滚的本地修改可直接执行；只有用户明确要求先给计划时，才先给计划并等待确认。计划说明目标、范围、关键步骤、验证及提交推送边界。
- 远端写入、生产操作、部署、推送、破坏性操作、范围较大修改或存在覆盖风险时，先说明目标、范围与风险并取得相应授权；已授权范围内无需逐步重复确认，超出范围时重新说明。
- 只有用户明确要求 `ga`、`gc`、提交或推送时才暂存、提交或推送；始终排除环境配置、临时文件和无关改动。提交信息默认使用中文，仓库约定或用户要求更具体时从其约定。
- 任务完成后区分已完成、已验证和未验证事项。工具返回成功或请求被接受不能单独证明结果符合预期。
- Subagent 工具可用、策略允许且存在能与主任务并行的独立明确子任务时，主动委派；明确范围和禁止扩展的边界，主 agent 核对原始文件并负责最终修改和验证。失败或结果不完整时由主 agent 收回继续。

## 经验与证据

- 按任务关键词定位适用经验，并用当前文件、配置、命令输出或接口响应核对；不直接采信旧经验。
- 任务结束前判断是否需要更新已有经验。只记录可复用的判断、边界、风险和验证方法，不记录一次性的地址、ID、数量、执行流水或当前状态；合并近义条目，并按通用或项目范围写在本文件对应章节。写入后复读，检查重复、抽象层级和敏感信息；最终回复简要说明经验处理结果。
- 用户指出结果异常、缺失、被覆盖或与预期不符时，立即停止扩散修改，读取真实状态并核对同批次对象、字段、接口、配置及关联数据。修复后再次独立回读；由自身操作造成且可复用的失败模式需记录现象、根因、错误做法、正确做法、影响检查和验证方式。
- 修改外部系统、远程配置、接口文档、数据库或缓存前，先读取并保留原结构、引用关系、标识和必要元数据；写后用独立读取、查询、导出或界面结果验证关键字段、关联与行为。修复不得自行扩大为新的远端写入、数据库修改、删除、部署、推送或批量修改。

### 常见场景

- Bash 脚本若可能由 `sh script.sh` 调用，确保 shebang 从首字节开始；使用 `pipefail`、`[[ ... ]]` 等 Bash 语法前检测 `BASH_VERSION` 并可通过 `exec bash "$0" "$@"` 切换。不要为兼容而删除 `pipefail`；注意下游提前退出引发 SIGPIPE 141，动态匹配反引号时避免 Shell 命令替换。用 `bash -n`、用户原始调用方式及产物完整性与校验文件回读验证。
- 本地微应用端口被占用时，先查监听进程、工作目录和页面标识确认原应用；不停止用户现有进程。选择空闲端口后同步调整微应用开发服务的 `port/origin` 和主应用加载 `entry`；HTTP 200 之外还须核对标题、根节点或源码入口，本地验证配置不扩散到测试或正式环境。
- 安装、迁移或升级应用时，按应用名、系统、安装方式与目标路径查经验并核对当前安装包、目录、配置和验证结果；只有可复用的兼容性边界与验证方法写入经验，不记录单次版本、下载地址或执行状态。

## 业务接口与凭据

- 查询或修改当前运行环境的业务数据时，默认优先使用业务接口；此规则不限制代码阅读、静态分析或离线处理。接口用法不清楚时依次核对既有经验、前端真实请求、后端 Controller 与模型，再结合网关路径、租户和终端还原调用，不凭接口名或旧参数猜测。
- 接口调用后检查状态码、业务响应和关键字段；写操作还需通过详情、列表或对应查询独立回读。接口不存在、环境不可达或鉴权缺失时，可在原授权范围内使用其他数据源，并说明原因和验证边界。
- 直接执行数据库 `insert`、`update`、`delete`、DDL 或等价写操作必须取得明确授权；接口不可用不构成改库授权。获准后仍需说明绕过业务校验、事件、缓存和关联维护的风险，并回读关联数据。
- 只使用当前会话的凭据。规则、Skill、源码、日志和回复中不得记录真实 Authorization、Cookie、Token、密码、密钥、验证码或完整敏感请求体。记录测试请求时只保留 Host、路径、Header 名称、tenant、terminal、content-type、Referer 等请求形状；凭据字段仅用脱敏占位值。

## 规则与 Skill 同步

- 本仓库 `codex/AGENTS.md` 是规则与经验的权威源；本机 Codex 的全局入口是 `~/.codex/AGENTS.md`，`~/.codex/agents/` 存放子代理配置，不是全局规则入口。修改仓库入口前先比较并保留本机入口的有效差异，修改后同步到当前环境的全局入口并以 `cmp`、`diff` 或等价方式核对。不要维护 `~/.codex/codex/` 旧镜像。
- 用户要求同步或备份 Codex 规则时，确认当前工作目录和仓库状态并获取远端最新提交，以远端规则为基线逐项合并当前有效规则；双方同一规则语义冲突且无法判断时询问。认证文件、配置数据库、日志和缓存不纳入同步。Git 提交或推送仍以用户明确要求为准。
- 自定义 Skill 统一保存在 `codex/skills/<skill-name>/`，与当前环境 `~/.codex/skills/<skill-name>/` 的副本双向比较并保留双方有效修改；保留 `SKILL.md`、`agents/` 和实际需要的 `references/`、`scripts/`、`assets/`，同步后比较文件清单与内容。
- Skill 及副本不得包含运行时凭据或会话文件。`.system` 内置 Skill、插件缓存和第三方安装 Skill 不纳入本仓库同步，除非用户明确要求；删除仅限用户明确指定的 Skill 及其副本。

## 编码通则

- 除非用户明确要求执行构建，否则不主动运行任何完整或局部构建，包括 Bazel、Maven、Gradle 及 npm/pnpm/yarn/bun 的 build。默认优先源码检查、`git diff --check`、格式或静态检查，以及已授权的定向测试；交付时说明未执行的验证及剩余边界。
- 在不影响业务语义、接口契约、运行逻辑和可维护性的前提下，代码精简、直接、无冗余。只实现当前需求，优先复用现有模型、工具、常量、客户端、服务和标准库；不重复封装通用判空、字符串、集合、分页、JSON 或异常工具。
- 稳定、封闭且具有分支、校验或行为语义的状态、类型、来源、阶段、级别等有限值域，优先按项目约定用枚举；动态字典、配置、外部协议和用户维护的开放值域保留未知值及演进边界。稳定业务字符串按边界复用常量或值对象，不散落硬编码。
- Java 类与方法按业务域和职责归属拆分，保持单一职责。Service 按资源和职责拆分；已有接口时 Controller 依赖接口，简单单实现服务不机械抽接口。复杂参数校验、转换、外部数据补全、配置解析和指标组装按实际需要放入 Assembler、Validator、Provider、Manager 或 Helper，避免语义不明的根包 `*Support` 集合。
- Controller 按业务域和资源边界拆分，新接口先判断是否有合适的现有 Controller。公共契约、非显然字段和关键业务边界添加准确简洁的注释，名称和类型已充分表达时不机械补注释。
- 不在循环中调用数据库 mapper/service/repository 的读写方法，也不在循环中调用内外部 client；优先批量查询、写入或一次性调用。确实无法批量化时先说明原因、影响和风险并取得确认。跨模块能力优先复用已有 client；新增前说明现有能力的不足和影响范围。
- 外部领域对象的展示、详情补全、实时状态或历史数据优先来自权威服务、已有 client 或配置中心；业务模块不复制外部数据源、不保存无必要的展示快照、不跨库直连外部领域表。
- 业务校验失败使用项目统一异常和既有错误码，不用裸 `RuntimeException` 或 `IllegalArgumentException` 替代。`IllegalArgumentException` 仅用于编程接口前置条件等非业务边界。
- 业务日期时间使用项目统一类型和数据库字段类型，不随意用字符串、纯日期或时间戳承载需要精确到时间的值。
- 在外部系统边界、批量汇总、关键状态变化和异常处记录有诊断价值的日志；包括必要的业务标识、租户、数量和目标，不机械记录方法开始结束，也不在循环中打印大量逐条日志。不得记录敏感凭据和完整请求体。
- 前端应用提交业务源码、样式或资源时，默认把每个实际变更应用的 `package.json` patch 版本递增 1；用户明确免升、仓库另有版本源或规范禁止时除外。提交前按目标分支基线执行已有版本门禁，确认版本严格高于基线；只处理本次应用，lockfile 以仓库约定和校验结果为准。

## Codebase Memory

- 结构化代码发现优先使用图谱：`search_graph` 查符号、`trace_path` 查调用、`get_code_snippet` 读精确源码、`query_graph` 查复杂关系、`get_architecture` 看结构。字面量、配置和非代码文件可直接用 `rg` 或文件读取。
- 每次会话开始或上下文压缩后，用 `list_projects` 或 `index_status` 确认索引代际。Scout 仅做暂定的快速发现；Verify 核对方向和源码；Auditor 在限定范围内核对代际、分页、必要双向关系与限制。
- 图谱有 `has_more` 或 `nextCursor` 时读取任务相关后续页；对依赖文件及否定结论涉及的范围调用 `check_index_coverage`。索引缺失、过期、不完整或未知时直接读源码；无记录缺口不等于完整覆盖。委派代码结构调查前把索引、覆盖和源码回退结果传给子任务。

## Cube2 项目

- Cube2 分管理端与用户端。处理应用、菜单、角色和权限前先确定所属终端，不能跨端复用配置。OUAA 菜单的查询、增删改属于管理端；测试环境的管理端菜单请求使用 `tenant: 0`、`terminal: kh-admin-web`，管理员鉴权仅用调用当次会话。
- 应用 ID、父菜单、路径、编码、排序从当前应用实时菜单树确定，不从其他应用或历史记录硬编码。菜单写前读取现有树，写后独立回读名称、应用、父级、路径、排序与启用状态。新增菜单不自动授权普通用户角色；用户端可见性需在明确授权范围内配置角色菜单关系，并核对用户端的终端、应用与角色。
- OUAA 菜单和角色授权优先使用 `$cube2-menu-management`；租户字典、字典项及 AI Flow 字典配置优先使用 `$cube2-dictionary-management`。遵循对应 Skill 的实时解析、预读、当前会话鉴权与写后回读要求。
- 接口调试先确认环境、应用、租户及终端。本地请求为 `http://localhost:<用户确认的端口>/<接口路径>`，端口必须在调用前向用户确认。记录的测试环境模板为 `https://cube-test.guhecloud.com:3000/api/<网关前缀>/<接口路径>`；网关前缀从目标应用 `server/BUILD.bazel` 的 `server_info.gw_prefix` 实时核对。
- 普通 Cube2 接口请求模板的 Header 包含当前确认的 `tenant`、`terminal: bimops-manage-web`、`Authorization: Bearer ${CUBE2_BEARER_TOKEN}`、`User-Agent: Apifox/1.0.0 (https://apifox.com)`、`Content-Type: application/json`、`Accept: */*`、按环境生成的 `Host` 及 `Connection: keep-alive`。此普通模板不能替代上述 OUAA 管理端菜单的终端上下文；不得从模板推断具体应用、网关、租户或真实 Token。

## ghcloud 项目

- 开始任务先读取仓库根 `.agents/README.md`，再按当前任务读取它指向的仓库地图、Skill、标准和命令文档；命中目录后读取最近层级的 `AGENTS.md`、目标 Skill、包的 `package.json` 和实际 scripts。当前代码、类型、构建配置与脚本是最高优先级事实，文档冲突时以当前实现为准。
- `prod` 按当前标准结构处理；`legacy` 保持最小必要修改，不顺手现代化、重构或升级依赖。遵循目标文件现有 TypeScript、Vue、样式与格式化风格，不做无关大范围格式化。命令、测试和构建从目标包脚本及 `.agents` Skill 发现，不按目录名猜测。
- 服务契约、BFF、SDK 或前端接口调用先读 `.agents/standards/cube-service-contracts.md`。`prod/cube-services/` 契约变更同步核对 `interfaces`、`gateway`、`client`；未改变契约时不无故修改其他层。需认证的 BFF 调用使用 `@ghcloud/cube-services-client/auth-request` 中的 `authRequest` 或 `useAuthRequest`，不复制 Token、租户或请求头处理。
- 修改 `@dangao/bun-server` 的 Controller、代理、鉴权透传或拦截器前，读取对应 Bun Server Skill 并沿用 DI、装饰器和请求上下文模式。维护 legacy 既有 `api` 目录时按当前实现最小补齐；新服务能力优先采用 `@ghcloud/cube-services-client`，缺契约时按三层结构补充。
- 环境地址、认证和部署信息从当前环境资料与实时状态核对，不跨环境复用。未经要求不改生成物、`dist/`、`lib/` 或无关 lockfile；依赖安装需用户明确授权。

### 经验

- Vue、qiankun、Pinia、路由、BFF 或 SDK 问题，连同共享接口类型、Gateway、Client 和前端调用核对。日期范围清空后可能仍含空槽，不能直接可选链 `join(",")`；发送前验证起止值，无效则省略参数，并检查同页其他时间筛选。
- 参考旧页新增独立页面时，除字段与列表接口，还要核对筛选清除、页头操作、权限、导出参数和下载行为；反向命名的组件参数要读实现。legacy 同类设备接口包装不能只凭函数存在判断可用，先找同应用真实调用页，复用 API 名称、应用编码和行主键，再对照当前实体、VO 与响应核字段。
- 构建、启动或推送前检查失败时，先查目标包脚本、workspace 依赖、catalog、lockfile 及 Node/Bun 环境，再判断代码或环境原因；watcher、版本、lockfile 和 workspace 协议问题不直接归因业务代码。
- 前端 Git 提交、回退或发布使用路径限定的暂存和提交，区分业务文件、环境配置和 lockfile，核对缓存区差异及实际验证。不要套用其他仓库的分支、发布脚本或历史失败经验。
- legacy qiankun 页面空白或返回白屏时，先查真实路由和子应用根布局；页面外侧空白只调整页面根容器，保留面板内部层次。固定返回地址直接使用目标路由，不用浏览器历史长度猜测；legacy 经验不反推 prod 规范。

## Kaihe 项目

- 仓库根 `AGENTS.md` 是项目入口；按其路由读取目标文档最近层级的 README、`.kilo/rules/` 和匹配的 `.kilo/skills/`。需求与原型先从 `docs/需求文档/README.md`、`docs/产品原型/README.md` 及目标目录 README 定位，结合当前文件、Frontmatter、版本历史和真实导航关系判断权威版本。
- 用户指定具体文件或路径时先检查该来源；未指定时按 README 路由，不默认读取 `archive/` 或个人历史目录。环境路径和外部资料只从当前环境或用户明确输入获取，不把单台机器路径提升为跨环境事实。
- 需求文档用于确认明确业务规则，原型用于核对页面、字段、展示对象、触发来源和交互。跨文档结论区分直接依据与推断；原型分析追踪入口、导航、链接和 iframe 关系，不只看孤立页面。

### 经验

- 需求到代码或数据结构的追踪按“需求文档 -> 原型入口与页面 -> 当前项目代码 -> 数据结构”进行；页面字段不能仅凭截图或单个 HTML 推断，要核对入口导航、原型与需求。
- 页面显示、滚动、iframe 或入口流程异常时先确认真实打开路径，再追踪导航和真正拥有事件、滚动的容器；原型单独打开正常不代表产品入口正常。
- 需求、AI 结论、法规和量化数据要保留来源、版本与推断边界；法规绑定具体条款，数据绑定可追溯来源。Kaihe 的角色、页面、语义与文档结构不直接当作其他项目事实。

## Kaiyun OA 项目

以下约束用于新增或修改的 Kaiyun OA Java 代码。

- 具有业务语义的分支、提前返回、降级或跳过、`try/catch`、外部调用和状态变化须有可追踪日志。关键阶段记录操作、步骤、结果及必要安全标识，复用租户、TraceId、任务名或实体 ID；外部 client、数据库、消息和文件边界记录关键状态，批量记录总量、成功、跳过、失败及耗时或失败摘要。
- `catch` 记录异常上下文和完整堆栈，不只写 `getMessage()`。`INFO` 用于业务里程碑与最终结果，`DEBUG` 用于详细分支，`WARN` 用于可恢复异常、降级和跳过，`ERROR` 用于失败与堆栈；循环内避免逐条大量 `INFO`。
- 新增或修改的 Controller 类与端点、请求/响应 VO、数据库实体类与字段必须有准确注释。说明业务用途、字段含义、单位、格式、是否必填、取值范围和特殊语义；状态码、枚举、关联及非直观转换优先在定义处说明，不写空泛注释。
- 稳定、有限且有业务语义的值域必须使用枚举，VO、DTO、Command、Query、领域对象及 ORM Entity 可直接使用枚举字段。仅在数据库、历史兼容、外部协议或框架序列化明确要求时在边界保留基础类型，并由 Mapper、Assembler 或 TypeHandler 集中转换；业务逻辑内部用枚举，不重复定义同一值域。开放值域保留未知值边界。
- 新增或修改的请求、响应、VO、DTO、Command、Query 及其他纯数据载体使用 Java `record`，组件配准确注释，不用可变 Setter 隐藏契约；只有 ORM 生命周期、代理、序列化、继承等明确技术约束时使用普通 `class`，并在变更说明中写明原因。
- Java 类型在文件顶部 `import` 后使用，不在声明、签名、泛型、注解或业务代码中直接写完整包名。先用分层命名化解同名冲突；框架要求的字符串类名或包名配置不受此条限制。
