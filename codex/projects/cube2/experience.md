# Cube2 项目经验总结

本文档只记录能够指导 Cube2 同类任务的判断方法、操作边界和验证方式。具体环境、租户、对象、ID、地址、数量及一次性执行结果应保留在任务结果或对应环境经验中，不在本文件中按任务逐条累积。

## 后端实现、分层与既有能力复用

- 适用场景：新增或修改 Cube2 后端能力，或需要判断代码应放入 `apps`、`base`、`platform`、`customization` 的哪个边界。
- 判断与做法：先根据业务词、接口路径、网关前缀、表名或 Controller 定位应用，再读取最近的模块 `SKILL.md`、`AGENTS.md` 和相似实现。应用独占流程留在 `apps`，多应用复用的领域能力优先进入 `base`，横切技术能力优先复用 `platform`，客户特化逻辑放入 `customization`。跨领域数据优先复用已有 client，不重复建设数据源或服务封装；Controller 和 Service 按业务边界拆分，复杂校验、转换和数据补全放入职责明确的组件。
- 边界与验证：禁止在循环中调用数据库或 client，应改为批量查询、批量写入或一次性调用；不得因局部需求主动改变既有分层、发布形态或引入新基础设施。默认使用源码检查、目标测试和 `git diff --check` 验证，不自动执行完整 `bazel build`。

## 接口调试与错误分层

- 适用场景：接口返回 401、403、业务前置错误、500，或响应存在多层包装、下游转发和字段结构不稳定。
- 判断与做法：按“前端真实请求 → 网关路径 → Controller 参数 → 下游 client/Feign 参数 → 业务响应字段”逐层核对，区分认证失败、租户或终端上下文缺失、业务配置不完整、参数未透传和下游异常。代理接口接收了参数不代表已传给下游，应检查请求对象的实际构造过程；解析响应前先确认数组、包装对象和真正业务结果所在层级。
- 边界与验证：鉴权信息只使用用户当前会话提供的有效值，不复用历史 Token 或 Cookie。HTTP 200、`true`、空响应体或工具成功状态只能证明请求被接受；必须继续检查业务码、关键字段，并通过详情或列表接口独立回读。前端保留旧数据或旧坐标时，先确认请求是否失败，不要直接修改展示逻辑。

## 配置与数据写操作闭环

- 适用场景：修改字典、规则、应用配置、设备绑定、档案配置或其他具有引用关系的业务对象。
- 判断与做法：写入前通过权威业务接口读取完整现状、引用关系和必要元数据，明确接口是局部更新还是整对象覆盖；整对象更新必须保留未修改的条件组、动作、编码和关联字段。业务接口能够完成时优先走接口，以保留校验、事件、缓存和关联维护；接口不存在或不能覆盖目标时才降级到数据库，并说明影响。
- 边界与验证：批量操作失败或超时时不能假设全部回滚，应重新读取确认是否部分落地，再根据真实状态补齐。每次写入后使用独立查询核对关键字段、引用关系和同批次影响范围；保留新增或变更标识，优先采用可追踪更新和软删除，不用删除重建代替可回滚修改。

## 应用、访问端、菜单与权限链路

- 适用场景：应用菜单缺失、菜单页面空白、页面路由存在但侧栏无入口，或需要跨环境补齐应用和菜单。
- 判断与做法：把应用、访问端、菜单父子树和角色授权视为完整链路。新增或同步前先读取目标环境的应用、访问端和现有菜单，以已验证的同类配置作为字段模板；已有应用只补缺失菜单，缺失应用先确认应用分组和编码再创建。页面无数据时先核对前端真实请求是否同时携带正确的访问端和应用参数，再检查数据库条件和父子关系。
- 边界与验证：创建菜单不会自动完成角色授权，数据库有菜单也不代表运行端可见；写入后应按应用和访问端回查菜单数量、父子层级、路径、排序、启用状态、普通角色映射及运行端菜单响应。模板数据源必须确认连接到了真实业务 schema，系统 schema 的空结果不能作为同步依据。

## 跨环境与跨数据库数据同步

- 适用场景：在不同环境、数据库类型或 schema 之间同步业务配置和数据。
- 判断与做法：同步前逐表核对源和目标的表存在性、字段名称、类型、精度、唯一约束和数据量，按列名显式映射而不是依赖字段顺序。持续变化的数据先固定源快照，再使用参数化批量写入或可控的小批次同步；大文本可通过摘要比较，时间字段需明确两端精度及舍入行为。
- 边界与验证：字段缺失时不能静默丢弃，应先补结构或由用户确认排除；批量请求超时后先检查部分落地情况。19 位 ID 在 JavaScript 中必须使用字符串或 `BigInt`，不能经由 `Number` 运算。完成后逐表核对数量、关键字段、唯一有效记录和引用关系，不能用稍后变化的源数据否定固定快照的同步结果。

## 测试造数、唯一标识与可回滚验证

- 适用场景：为定时任务、趋势、告警、档案或业务流程构造测试数据。
- 判断与做法：先读取当前配置、字典、产品模型、业务前置状态和唯一约束，再按真实触发条件设计数据；不能只满足单个阈值而忽略连续天数、递增关系、状态去重、属性类型等组合条件。优先使用业务批量接口，记录原始数据和本次审计标识，新增 ID 必须在目标类型范围内并避开已有值，采集时间应满足唯一约束。
- 边界与验证：生成属性值前检查物模型约束，避免平台截断；同一设备、属性和时间戳的重复上报未必覆盖旧值，不能用重复写入假定修正成功。禁止用删除重建替代可追踪更新；造数后同时验证记录数量、时间范围、首末值、关联完整性、业务接口结果和页面展示，并准备基于本次标识的逻辑回滚方案。

## 产品、设备、绑定与标识一致性

- 适用场景：产品接入、设备创建或重命名、业务对象绑定、区域归属、应用设备筛选及设备数据查空。
- 判断与做法：先区分产品 ID、设备中心实例 ID、三方设备 ID、业务对象 ID、雷达或主设备标识及区域级联路径等不同标识，沿权威接口确认每个字段的来源和语义。候选设备在写入绑定前必须通过设备详情确认仍然有效，并按产品、末级品类和业务归属筛选；批量更新设备时保留接口要求的原编码等必填字段，避免省略字段被覆盖为空。
- 边界与验证：同一业务对象可绑定多台设备不代表同一设备可跨对象重复绑定，应按设备中心 ID 做全局唯一性检查。产品直接初始化时还要补齐分页转换依赖的品类、品牌、接入方式、协议和节点类型等元数据。应用设备可见性可能同时依赖应用标签和租户设备引用，写入后应从设备详情、业务绑定分页和应用设备接口三个方向交叉验证。

## 告警规则、物联事件与业务落库链路

- 适用场景：新增产品属性告警规则、模拟设备上报，或规则显示命中但业务告警未生成。
- 判断与做法：规则创建前读取应用关联产品、产品模型属性、单位、约束和业务前置配置；需要指定设备时从权威绑定关系中筛选，整条规则更新必须保留原条件、时段、阈值和动作。规则应通过业务服务创建以发布物联联动，不能直接写应急或告警表。模拟上报后按“实时属性 → 规则匹配快照 → 联动事件 → 动作终态 → 业务告警记录”逐层排查。
- 边界与验证：上报接口成功、通知成功或动作进入执行中都不等于告警已经落库；异步动作需要轮询终态并同时回查告警记录。消息快照、设备标识或触发时间为空可能使消费链路在业务事件发布前中断，应沿消费者契约检查可靠回退来源。连续超阈值没有新事件时，先确认规则是否采用状态跃迁语义，必要时上报恢复值并等待消费完成后再重新触发。

## 字段下线与业务契约迁移

- 适用场景：删除页面字段、下线定时任务、替换业务类型或调整前后端字段契约。
- 判断与做法：按后端角色或枚举、识别关键词、DTO/VO、Mapper、计算映射、告警字段、导出列、前端类型、响应解析、图例和页面组件建立完整影响清单。字段不再展示不等于权威数据可以删除；先全仓检索其他统计、同步、设备和三维等消费者，再只清理独占代码与依赖。类型迁移还要同步核对环境中的设备名称、规则名称、单位换算和历史数据语义。
- 边界与验证：不能用全仓机械替换代替契约分析，也不能把页面下线扩大为删除底层数据。删除监听器、附属表访问或任务前，应确认无 Controller、前端、事件和其他服务消费者；数据库迁移记录显示执行过不代表目标表现存，边界状态才触发的清理逻辑应使用真实表结构和完整业务路径验证。

## 档案、趋势、导出与看板数据口径

- 适用场景：同一业务对象在基本信息、分页、趋势、导出或看板中的数值和状态不一致。
- 判断与做法：先确定权威数据源和写入链路，基本信息、明细、趋势和导出应复用同一数据源、同一组字段语义和同一计算规则；相邻记录差值必须使用一致的排序和分组。分页接口返回持久化字段时不能误判为实时统计，应继续追踪设备消息、配置刷新或定时任务如何更新该字段。
- 边界与验证：数据查询范围和图表横轴范围可以不同，例如趋势保留固定空桶而分页和导出过滤全空占位行；当前日期查询必须避免未来数据通过时间扩展或邻近匹配进入结果。时间字段可能以日期字符串、毫秒值或数字字符串返回，前端应先归一化再生成标签。最终交叉核对接口明细、聚合结果、导出内容和页面展示，避免不同页面自行反转符号或重新解释状态。

## 时间维度统计、分桶与兼容

- 适用场景：统计接口需要同时支持今日、本周、本月和年度，或新增时间维度后旧接口行为发生变化。
- 判断与做法：先明确各维度的查询区间、对比区间和聚合粒度：今日通常按小时，周和月按天，年按月。保留旧接口及旧方法的既有语义，为通用查询新增参数模型或重载，再让新入口按维度选择聚合策略；平台日期工具缺少某个时间单位时应在通用能力中补齐，而不是在业务页面规避。
- 边界与验证：SQL 分桶键必须包含完整年月日或年月，不能只用日号或月号导致跨月、跨年合并；月统计使用实际天数，所有维度按约定补齐空桶。测试至少覆盖旧接口小时语义、跨月周、正负偏移、跨年边界、本月实际天数、全年月份和无数据场景，并验证当前周期与上一周期都能正确生成。

## 微应用看板、异步加载与图表状态

- 适用场景：多个接口共同驱动看板、局部请求失败导致整页空白、微应用跳转异常，或 ECharts 在数据量变化后报内部状态错误。
- 判断与做法：相互独立的统计、列表和告警请求可并行发起，但应在各自返回后立即更新对应区域，并使用区域级加载和错误状态；聚合等待使用能够保留部分成功结果的方式，避免单个请求失败清空其他数据。微应用内部已有目标页面时优先使用当前路由，跨应用跳转前确认目标应用实际从 URL、会话存储还是主壳上下文读取筛选条件。
- 边界与验证：ECharts 实例使用 `shallowRef` 或 `markRaw`，避免深层响应式代理破坏内部坐标系，也避免 watcher 与请求回调重复合并同一套 option。图例和刻度重叠等布局问题优先调整网格留白，不修改业务数值规避。接口失败时页面可能保留旧状态；部署后仍无变化时还应核对提交推送、微应用入口、构建哈希和静态资源是否确实更新。
