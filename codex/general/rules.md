# 通用规则

本文件记录可迁移到其他 Codex 环境的通用协作和编码规则。

## Codex 环境变量强制要求

- `CODEX_WORK_ENV` 是规则路由的硬前置条件，当前支持 `ghy`、`home-windows` 和 `home-wsl`。
- 每次任务由 `codex/AGENTS.md` 校验环境并路由到 `codex/envs/<env>/AGENTS.md`；变量为空或值不受支持时停止具体操作并提示用户配置。

## 项目规则执行

- 用户明确指定的仓库、绝对路径或可唯一定位的项目优先；未指定时才以当前工作目录所在仓库为目标。跨仓库任务逐个匹配，新增目标时先完成对应路由。
- 以当前环境 `AGENTS.md` 指定的工作区根路径匹配完整项目根路径及其子目录，不根据子目录名称猜测项目；Windows 的 WSL UNC 路径按对应的 WSL 路径匹配。项目目录与规则目录的映射为：`cube2-upgrade` → `codex/projects/cube2/`、`ghcloud` → `codex/projects/ghcloud/`、`kaihe` → `codex/projects/kaihe/`、`kaiyun-oa` → `codex/projects/kaiyun-oa/`、`baseline` → `codex/projects/baseline/`。
- 匹配项目后，读取其规则目录下存在的 `rules.md`，按任务关键词检索存在的 `experience.md`；缺失的可选文件跳过，不用其他项目文件替代。未匹配的目标不加载项目级资料。
- 确定实际操作项目后，必须严格执行该项目匹配的每一条规则，不得按个人偏好选择性跳过或降低要求。
- 通用规则、环境规则与项目规则同时适用；规则冲突时按更具体的项目规则优先，无法判断时暂停相关操作并询问用户。
- 编写、修改、重构、格式化、自动生成或批量改写项目代码前，必须完整读取该项目规则目录下的 `CODING_STANDARDS.md` 并逐条遵守；文件缺失、无法完整读取或内容不明确时停止该项目代码操作并报告，不得用其他项目规范代替。
- 代码操作后按该项目 `CODING_STANDARDS.md` 逐条复核，并结合源码扫描、差异检查或适用的定向验证确认符合性；未通过时先修复或明确报告，不得宣称完成。

## Subagent 协作

- 当前 subagent 工具可用、运行策略允许，且任务中存在目标明确、可独立委派并能与主 agent 的有效工作并行推进的子任务时，必须主动使用 subagent，不得仅因任务简单或主 agent 能自行完成而跳过；工具不可用、运行策略禁止或任务确实无法独立拆分时，由主 agent 直接执行并简要说明原因，不得制造无意义的拆分或重复工作。
- 委派时明确目标、范围、输入、输出和禁止扩展的边界；subagent 结果只作为证据或候选修改，由主 agent 核对原始文件并负责最终修改和验证。
- subagent 失败、超时或结果不完整时，主 agent 收回任务继续推进，不让委派阻塞主流程。

## 经验总结与抽象质量高优先级规则

- 任务开始时读取当前环境 `AGENTS.md`，并用任务关键词检索通用及所有目标项目的经验，只读取命中条目及必要上下文；没有命中时无需全文读取。
- 经验只能辅助缩小范围，不能替代当前文件、配置、命令输出或接口响应。需要执行计划时，简要说明命中的经验或未发现相似经验。
- 任务结束前判断应优化已有经验、追加新经验还是无需变更；只有能指导同类任务的稳定判断、边界、风险或验证方法才写入，不记录一次性对象、地址、ID、数量、执行流水和当前状态。
- 写入经验时优先合并近义条目，并按适用范围归类：跨环境、跨项目适用的写入通用经验；只适用于某个项目且可跨环境复用的写入项目经验；只与某个环境的路径、配置、账号、工具或机器状态相关的写入该环境的 `AGENTS.md`。不确定归属时询问用户。
- 写入后复读目标条目，检查重复、抽象层级和敏感信息；项目经验不得因当前运行环境不同而重复写入环境经验。
- 最终回复简要说明经验处理结果；经验复查不得自行扩大代码、配置、提交或推送范围。

## 业务接口优先

- 查询或修改当前运行环境中的业务数据时，默认优先使用该环境的业务接口；本规则不替代代码阅读、静态分析、离线数据处理或其他不操作当前环境业务数据的任务路径。
- 不清楚接口如何调用时，按“既有经验 -> 前端项目中的真实请求代码 -> 后端项目中的 Controller、请求参数和响应模型”顺序核对，结合当前环境的网关路径、租户和终端约定还原实际调用方式，不得凭接口名称或历史参数猜测。
- 接口调用后必须检查状态码、业务响应和关键字段；写操作还必须通过详情、列表或对应查询接口独立回读，不能只根据请求成功判断任务完成。
- 接口不存在、当前环境不可达、鉴权条件缺失或接口无法覆盖任务目标时，可在原任务授权范围内降级使用其他数据源，并在执行说明和最终结果中明确原因、影响范围及验证方式。
- 直接执行数据库 `insert`、`update`、`delete`、DDL 或等价写操作必须取得用户明确授权；接口不可用不构成改库授权。获准后仍需说明绕过业务校验、事件、缓存和关联维护的风险，并回读关联数据与最终业务结果。

## AI 失误复盘与验证

- 用户指出结果异常、缺失、被覆盖或与预期不符时，必须立即停止继续扩散修改，先读取真实状态并核对本次操作的完整影响范围。
- 不能只修复用户截图中暴露的表象；必须检查同批次修改的其他对象、字段、接口、配置和关联数据是否存在相同问题。
- 修改外部系统、远程配置、接口文档、数据库或缓存前，必须先读取并保留原有结构、引用关系、标识和必要元数据；不得用不完整的新结构覆盖原对象。
- 工具返回 `success`、零错误或成功状态码只能证明请求被接受，不能作为任务完成依据。写操作后必须通过独立读取、查询、导出、接口调用或界面结果验证关键字段和行为。
- 修复失误后必须再次执行回读验证，并明确区分“写入成功”和“结果符合预期”；无法验证时不得宣称已完成。
- AI 自身操作导致错误且形成可复用失败模式时，按经验规则记录异常现象、直接根因、错误做法、正确做法、影响范围检查方式和最终验证方式。
- 用户已明确指出 AI 失误时，不得只道歉或口头承诺；需要在原任务已经授权的对象、系统和操作范围内完成修复与复核，除非缺少权限或外部条件。经验处理同样不得突破原授权范围。
- 修复不得把原任务授权扩展为新的远端写入、数据库修改、删除、部署、推送或批量修改；确需扩大范围时，先说明原因、目标和风险并取得用户授权。

## 任务计划按需触发

- 仅当用户明确提出“请给出计划”“先列计划”“先规划再执行”“只做计划”等同类意图时，才在具体任务操作前梳理并告知执行计划；是否触发以用户表达的计划意图为准，不机械匹配固定词语。
- 执行计划至少说明目标与范围、关键步骤、验证方式，以及是否涉及提交或推送；简单任务可以精简为一句话。
- 用户要求先给计划时，告知计划后停止具体任务操作并等待用户再次明确确认；确认前除环境校验、规则与经验加载所需的强制前置读取外，不得继续调用工具、执行命令、修改文件、调用接口或操作外部系统。
- 用户未明确要求计划时，不主动列出执行计划或等待计划确认；完成环境校验、规则与经验加载及必要说明后，按任务授权范围直接推进。
- 用户对计划的确认仅覆盖已告知的目标、范围和关键步骤；执行中需要扩大范围、改变关键方案或新增高风险操作时，必须重新说明并取得相应确认。

## 协作与执行

- 需要调用工具时，开始前先简要说明目标和范围。
- 普通的、范围明确且可回滚的本地修改，在说明目标和范围后直接执行；用户明确要求先给计划时，按“任务计划按需触发”规则等待确认。
- 远端写入、生产操作、部署、推送、破坏性操作、范围较大修改或存在覆盖风险时，即使用户未要求计划，也必须按对应规则说明目标、范围和风险并取得专项授权。
- 已确认计划或专项授权范围内的操作可以连续完成，无需对每个步骤重复确认；超出已确认范围时重新说明并取得确认。
- 计划按任务风险包含关键文件或系统、参考经验、验证方式以及是否提交或推送，不机械罗列无关项目。
- 完成后说明关键改动、验证结果和未验证项；工具成功或请求被接受不能替代结果验证。
- 只有用户明确要求 `ga`、`gc`、提交或推送时才暂存、提交或推送；始终排除环境配置、临时文件和无关改动。

## Codex 规则同步

- “同步 Codex 规则”和“备份 Codex 规则”统一执行同一个双向合并流程，不再区分两个方向；`dev-config-notes/codex/` 是规则与经验的唯一权威源。
- 同步开始时校验 `CODEX_WORK_ENV`，检查规则仓库状态并获取远端最新提交；仓库工作区改动和本机 `~/.codex/AGENTS.md` 入口改动都先读取并保留，不得在比较前覆盖。
- 以远端仓库最新规则为基线逐项合并当前有效规则；本机入口只作为候选输入，确认仍有效后先合并进仓库。双方修改同一规则且语义无法判断时停止并询问用户。
- 完成合并与验证后，以仓库中的 `codex/AGENTS.md` 覆盖本机 `~/.codex/AGENTS.md`，使本机入口成为权威源的副本；不维护或读取 `~/.codex/codex/` 规则镜像。
- 仓库入口 `codex/AGENTS.md` 新增、修改或合并时，在同一任务内先比较并保留本机入口的有效差异，再同步到当前环境的 Codex 应用目录；同步后使用 `cmp -s`、`diff` 或等价方式确认内容完全一致，失败时明确报告。
- 验证环境路由、文件引用、内容差异和 Git 变更范围；仓库有有效规则变更时，只提交并推送本次 `codex/` 文件。推送被拒绝时重新获取远端、合并并验证后再推送。
- 同步范围不包含 `auth.json`、`config.toml`、数据库、日志、缓存及其他认证或运行状态文件。

## Skill 同步

- 用户新增、修改或删除自定义 Skill 时，必须在同一任务内同步到当前环境的 `dev-config-notes/codex/` 规则仓库，不得只保留在本机 Codex Skill 目录。
- 项目专属 Skill 放在 `codex/projects/<project>/skills/<skill-name>/`，跨项目通用 Skill 放在 `codex/skills/<skill-name>/`，仅适用于一个工作环境的 Skill 可放在 `codex/envs/<env>/skills/<skill-name>/`；同步保留 `SKILL.md`、`agents/` 与实际需要的 `references/`、`scripts/`、`assets/`。
- 同步前读取并比较规则仓库对应 Skill，双方有效修改先合并，不得静默覆盖；删除时只删除用户明确指定的 Skill 及其副本。
- Skill 及其副本不得包含 Authorization、Cookie、Token、密码、密钥、会话文件或其他运行时凭据。`.system` 内置 Skill、插件缓存和第三方安装 Skill 不纳入同步，除非用户明确要求。
- 同步后比较本机与规则仓库副本的文件清单和内容；无法同步、验证失败或存在未解决冲突时明确报告。

## 应用安装与经验沉淀

- 安装、迁移或升级应用时，按应用名、操作系统、安装方式和目标路径检索相关经验，并核对当前安装包、目录、配置和验证结果。
- 只有形成可复用的兼容性边界、安装判断或验证方法时才更新经验；版本号、下载地址、临时路径和本次安装结果不单独沉淀。
- 未经用户要求，不因更新经验自动创建提交或推送。

## 基本编码原则

- **【必做】除非用户明确要求执行构建，否则不得主动运行任何完整或局部构建命令，包括但不限于 `bazel build`、`mvn package/install`、`gradle build`、`npm/pnpm/yarn/bun run build`。**
- 默认优先使用源码检查、`git diff --check`、格式或静态检查、用户已授权的定向测试进行验证；交付时明确说明未执行构建及剩余验证边界，不得为了“确认能编译”自行追加构建。
- 编写代码的第一重要准则：在不影响业务语义、接口契约、运行逻辑和可维护性的前提下，代码必须尽量精简、直接、无冗余。
- 不要引入不必要的抽象、包装、分支、临时变量、重复字段或重复逻辑。
- 优先复用当前项目已有的基础能力、工具类、模型、常量、客户端和标准库。
- 不要重复封装通用判空、字符串处理、集合/Map 处理、分页转换、JSON 处理、异常处理等基础工具，除非确实存在业务边界内的专用语义。

## 前端项目 Git 提交流程

- 提交前端应用的业务源码、样式或资源时，默认将每个实际变更应用当前 `package.json` 的 patch 版本递增 1，并把版本变更与对应业务提交一起处理；用户明确要求不升级、仓库使用其他版本源或仓库规范明确禁止时除外。
- 提交前按目标分支基线执行仓库已有的版本门禁或等价检查，确认目标应用新版本严格高于基线；只升级本次实际变更的应用，不修改无关包。
- lockfile 是否随版本变更提交以目标仓库实际约定和校验结果为准，不把无关 lockfile 漂移混入业务提交。

## Git 提交信息

- Git commit message 默认使用中文；仓库已有提交规范或用户明确指定语言时，优先遵循对应要求。

## 领域建模

- 对代码内部稳定、封闭且具有分支、校验或行为语义的状态、类型、来源、阶段、级别等有限值域，优先按项目约定使用枚举。
- 由数据库字典、配置中心、外部协议或用户动态维护的开放值域，不强制固化为枚举；需要类型约束时保留兼容未知值和版本演进的边界。
- 不要在业务代码、接口设计或表结构设计中散落重复、可复用的硬编码字符串。
- 稳定的业务字符串按业务边界复用常量或值对象；需要动态调整的内容通过配置或字典承载，不为一次性字面量机械创建常量。

## Java 后台职责拆分

- 编写 Java 代码时，优先按面向对象思想拆分职责。
- 类应保持单一职责。
- 方法应归属于合适的领域对象、服务对象、转换器、配置解析器或工具类中。
- 不应把无关逻辑集中堆叠在同一个类里。
- 对于功能相同或职责相近的类，应按业务域或技术职责单独建包统一管理。
- 抽象和拆包必须基于真实复用、复杂度隔离或边界清晰的需要，避免过度设计。

## Service 设计

- Service 必须按业务域、资源对象和职责边界拆分。
- 不要把不同职责堆到同一个 Service。
- Service 接口和 `*Impl` 结构遵循项目现有约定；存在多实现、稳定业务边界、跨模块契约或明确测试替换需求时再抽取接口，简单单实现服务不强制增加接口层。
- 已有业务接口时，Controller 依赖接口而不是具体实现。
- Service 实现应保持流程编排简洁。
- 复杂的参数校验、VO/DTO 转换、外部数据补全、配置解析、指标/趋势组装等逻辑，应按职责抽到专用组件、Assembler、Validator、Provider、Manager 或 Helper 中。
- 辅助组件也必须按业务域或技术职责继续分包。
- 包名要表达所属领域，类名要表达具体职责。
- 优先使用清晰后缀，如 `Assembler`、`Validator`、`Provider`、`Manager`。
- 不要把大量语义不明的 `*Support` 类堆在同一个根包下。

## Controller 设计

- 编写后台接口时，应根据业务域、资源对象和职责边界拆分不同 Controller。
- 不要把无关或弱相关接口全部堆到同一个 Controller。
- 新增接口前先判断是否已有合适 Controller；若没有，再按业务边界新建。
- 为公共接口契约、非显然字段、关键业务语义和重要边界添加简洁注释；名称和类型已经充分表达含义时不机械补充注释。
- 避免空泛、重复代码含义或与实现容易失同步的注释。

## 数据与外部调用

- 不要在循环中调用数据库。
- 不要在循环中调用外部或内部 client。
- 数据库操作包括 mapper/service/repository 的 select、insert、update、delete、save/remove 等。
- 应改为批量查询、批量写入或一次性 client 调用。
- 若确实必须在循环中调用，需要先向用户确认，并说明为什么无法批量化、影响范围和风险。
- 编写跨模块或跨服务能力时，若已有 client 或服务可复用，应优先复用现有能力。
- 不要新写重复 client、重复封装接口或重复建设数据源。
- 如果确实需要新增，应先告知用户新增原因、现有能力不能满足的点以及影响范围。

## 领域数据来源

- 编写涉及外部领域对象展示、详情补全、实时状态或历史数据的代码时，应优先从对应领域的权威服务、已有 client 或配置中心获取。
- 业务模块不要复制外部数据源、保存不必要的展示快照或跨库直连外部领域表。

## 异常处理

- 编写业务代码需要抛异常时，优先使用项目统一异常体系和既有错误码/消息机制。
- 业务校验失败不得用裸 `RuntimeException` 或 `IllegalArgumentException` 替代项目业务异常，也不要自造并行异常体系。
- `IllegalArgumentException` 只用于调用方违反编程接口前置条件等非业务边界，并应遵循项目现有约定；Controller 参数校验和领域规则失败仍使用对应校验或业务异常机制。

## 日期时间

- 编写涉及业务日期时间的代码时，应使用项目统一的日期时间类型和数据库字段类型。
- 不要用字符串、纯日期或时间戳随意承载需要精确到时间的业务时间。

## 日志

- 在外部系统边界、批量处理汇总、关键状态变化和异常处记录有诊断价值的日志，不机械添加方法或任务开始/结束日志。
- 日志按需包含业务标识、租户、数量、配置编码、任务名和外部调用目标；禁止记录 Token、Cookie、密码、验证码、完整请求体及其他敏感信息。
- 避免在循环中打印大量逐条日志。
- 批量场景优先记录汇总数量和失败摘要。

## Codebase Memory

- 结构化代码发现优先使用知识图谱：`search_graph` 查符号，`trace_path` 查调用，`get_code_snippet` 读精确源码，`query_graph` 查复杂关系，`get_architecture` 看整体结构。
- 每次会话开始或上下文压缩后，先用 `list_projects` 或 `index_status` 确认项目和索引代际。Scout 只做快速正向发现并标记为暂定；默认的 Verify 要核对相关调用方向和准确源码；Auditor 要在限定范围内核对当前代际、完整分页、必要的双向调用和广义关系，并说明限制。
- 图谱查询返回 `has_more` 或 `nextCursor` 时，继续读取任务相关的后续页，不得用被截断的结果作穷尽性结论。
- 确定候选路径后，在任何证据层级都对所依赖的全部文件调用一次 `check_index_coverage`；否定或穷尽性结论还要检查相关范围。无记录缺口不等于完整覆盖；索引不完整、过期或未知时直接读取对应源码范围。
- 字符串字面量、错误消息、配置和非代码文件可用 `rg` 或直接读取；图谱结果不足时也回退到源码。
- 委派子任务前，主 agent 先查询图谱和覆盖情况，并传递项目、代际、范围、查询分页状态、符号、路径、调用链、覆盖缺口、源码回退结果与待查问题；子 agent 不得假定自己有 MCP 访问权限。
