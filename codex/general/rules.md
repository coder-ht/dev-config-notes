# 通用规则

本文件记录可迁移到其他 Codex 环境的通用协作和编码规则。

## Codex 环境变量强制要求

- `CODEX_WORK_ENV` 是规则路由的硬前置条件，当前支持 `ghy`、`home-windows` 和 `home-wsl`。
- 每次任务按 `codex/AGENTS.md` 校验环境并加载对应规则；变量为空或值不受支持时停止具体操作并提示用户配置。

## Subagent 协作

- 仅在任务可以独立拆分、并行收益明显且当前运行策略允许时使用 subagent；简单任务、强耦合修改和统一判断任务由主 agent 直接完成。
- 委派时明确目标、范围、输入、输出和禁止扩展的边界；subagent 结果只作为证据或候选修改，由主 agent 核对原始文件并负责最终修改和验证。
- subagent 失败、超时或结果不完整时，主 agent 收回任务继续推进，不让委派阻塞主流程。

## 经验总结与抽象质量高优先级规则

- 任务开始时使用任务关键词检索通用、当前环境及匹配项目的经验，只读取命中条目及必要上下文；没有命中时无需全文读取。
- 经验只能辅助缩小范围，不能替代当前文件、配置、命令输出或接口响应。需要执行计划时，简要说明命中的经验或未发现相似经验。
- 任务结束前判断应优化已有经验、追加新经验还是无需变更；只有能指导同类任务的稳定判断、边界、风险或验证方法才写入，不记录一次性对象、地址、ID、数量、执行流水和当前状态。
- 写入经验时优先合并近义条目，并按“通用 / 当前环境 / 匹配项目”归类；不确定归属时询问用户。写入后复读目标条目，检查重复、抽象层级和敏感信息。
- 最终回复简要说明经验处理结果；经验复查不得自行扩大代码、配置、提交或推送范围。

## 业务接口优先

- 完成涉及业务数据的任务时，默认优先通过业务接口获取当前数据，不得在已有可用接口时直接把数据库查询、历史记忆或静态配置作为首选数据来源。
- 不清楚接口如何调用时，按“既有经验 -> 前端项目中的真实请求代码 -> 后端项目中的 Controller、请求参数和响应模型”顺序核对，结合当前环境的网关路径、租户和终端约定还原实际调用方式，不得凭接口名称或历史参数猜测。
- 接口调用后必须检查状态码、业务响应和关键字段；写操作还必须通过详情、列表或对应查询接口独立回读，不能只根据请求成功判断任务完成。
- 只有接口不存在、当前环境不可达、鉴权条件缺失或接口无法覆盖任务目标时，才允许降级使用数据库、配置或其他数据源；降级前应完成必要排查，并在执行说明和最终结果中明确原因、影响范围及验证方式。
- 涉及规则、流程、联动、缓存或领域事件的新增和修改时同样优先调用业务接口，避免直接改库绕过校验、事件发布、缓存刷新和关联数据维护；确需直接改库时必须说明风险并完成关联数据与最终业务结果回读。

## AI 失误复盘与验证

- 用户指出结果异常、缺失、被覆盖或与预期不符时，必须立即停止继续扩散修改，先读取真实状态并核对本次操作的完整影响范围。
- 不能只修复用户截图中暴露的表象；必须检查同批次修改的其他对象、字段、接口、配置和关联数据是否存在相同问题。
- 修改外部系统、远程配置、接口文档、数据库或缓存前，必须先读取并保留原有结构、引用关系、标识和必要元数据；不得用不完整的新结构覆盖原对象。
- 工具返回 `success`、零错误或成功状态码只能证明请求被接受，不能作为任务完成依据。写操作后必须通过独立读取、查询、导出、接口调用或界面结果验证关键字段和行为。
- 修复失误后必须再次执行回读验证，并明确区分“写入成功”和“结果符合预期”；无法验证时不得宣称已完成。
- AI 自身操作导致错误时，经验总结必须记录：异常现象、直接根因、错误做法、正确做法、影响范围检查方式和最终验证方式。
- 用户已明确指出 AI 失误时，不得只道歉或口头承诺；需要在当前任务范围内完成修复、复核和经验沉淀，除非缺少权限或外部条件。

## 协作与执行

- 需要调用工具时，开始前先简要说明目标和范围。
- 普通的、范围明确且可回滚的本地修改，在说明后直接执行；远端写入、生产操作、部署、推送、破坏性操作、范围较大的修改或存在覆盖风险时，先列出计划并等待用户确认，用户已明确要求直接执行时除外。
- 计划按任务风险包含关键文件或系统、参考经验、验证方式以及是否提交或推送，不机械罗列无关项目。
- 完成后说明关键改动、验证结果和未验证项；工具成功或请求被接受不能替代结果验证。
- 只有用户明确要求 `ga`、`gc`、提交或推送时才暂存、提交或推送；始终排除环境配置、临时文件和无关改动。

## Codex 规则同步

- “同步 Codex 规则”和“备份 Codex 规则”统一执行同一个双向合并流程，不再区分两个方向；`dev-config-notes/codex/` 是规则与经验的唯一权威源，`~/.codex/AGENTS.md` 只作为入口副本。
- 同步开始时校验 `CODEX_WORK_ENV`，检查规则仓库状态并获取远端最新提交；同时保留当前仓库工作区中的规则改动和本机入口改动，不得先覆盖或丢弃任何一方。
- 以远端仓库最新规则为基线，逐项合并当前有效规则：保留远端新增和修正，同时把本机尚未入库的有效规则合并到仓库；同一规则两边都修改且语义无法自动判断时停止并询问用户。
- 合并后让仓库规则、本机 `~/.codex/AGENTS.md` 入口保持一致；不维护或读取 `~/.codex/codex/` 规则镜像。
- 验证环境路由、文件引用、内容差异和 Git 变更范围；仓库有有效规则变更时，只提交并推送本次 `codex/` 文件。推送被拒绝时重新获取远端、合并并验证后再推送。
- 同步范围不包含 `auth.json`、`config.toml`、数据库、日志、缓存及其他认证或运行状态文件。

## 应用安装与经验沉淀

- 安装、迁移或升级应用时，按应用名、操作系统、安装方式和目标路径检索相关经验，并核对当前安装包、目录、配置和验证结果。
- 只有形成可复用的兼容性边界、安装判断或验证方法时才更新经验；版本号、下载地址、临时路径和本次安装结果不单独沉淀。
- 未经用户要求，不因更新经验自动创建提交或推送。

## 基本编码原则

- 编写代码的第一重要准则：在不影响业务语义、接口契约、运行逻辑和可维护性的前提下，代码必须尽量精简、直接、无冗余。
- 不要引入不必要的抽象、包装、分支、临时变量、重复字段或重复逻辑。
- 优先复用当前项目已有的基础能力、工具类、模型、常量、客户端和标准库。
- 不要重复封装通用判空、字符串处理、集合/Map 处理、分页转换、JSON 处理、异常处理等基础工具，除非确实存在业务边界内的专用语义。

## 前端项目 Git 提交流程

- 对前端应用执行 `ga&gc` 或等价流程前，先检查仓库或目标应用是否明确要求升级版本号；有要求时只升级本次应用，不修改无关包。
- 仓库没有版本升级约定时，不因普通提交自动修改 `package.json`。

## Git 提交信息

- Git commit message 默认使用中文；仓库已有提交规范或用户明确指定语言时，优先遵循对应要求。

## 领域建模

- 对于状态、类型、来源、阶段、级别等有限值域，能使用枚举的统一使用枚举。
- 不要在业务代码、接口设计或表结构设计中散落硬编码字符串。
- 编写代码时，不要在业务代码里硬编码可复用字符串。
- 若确实需要字符串常量，应按业务边界新增或复用常量类，或通过配置/字典承载，并通过统一引用使用。

## Java 后台职责拆分

- 编写 Java 代码时，优先按面向对象思想拆分职责。
- 类应保持单一职责。
- 方法应归属于合适的领域对象、服务对象、转换器、配置解析器或工具类中。
- 不应把无关逻辑集中堆叠在同一个类里。
- 对于功能相同或职责相近的类，应按业务域或技术职责单独建包统一管理。
- 抽象和拆包必须基于真实复用、复杂度隔离或边界清晰的需要，避免过度设计。

## Service 设计

- Service 必须按业务域、资源对象和职责边界拆分。
- 不要把不同职责堆到同一个 Service。
- Service 接口和 `*Impl` 结构遵循项目现有约定；存在多实现、稳定业务边界、跨模块契约或明确测试替换需求时再抽取接口，简单单实现服务不强制增加接口层。
- 已有业务接口时，Controller 依赖接口而不是具体实现。
- Service 实现应保持流程编排简洁。
- 复杂的参数校验、VO/DTO 转换、外部数据补全、配置解析、指标/趋势组装等逻辑，应按职责抽到专用组件、Assembler、Validator、Provider、Manager 或 Helper 中。
- 辅助组件也必须按业务域或技术职责继续分包。
- 包名要表达所属领域，类名要表达具体职责。
- 优先使用清晰后缀，如 `Assembler`、`Validator`、`Provider`、`Manager`。
- 不要把大量语义不明的 `*Support` 类堆在同一个根包下。

## Controller 设计

- 编写后台接口时，应根据业务域、资源对象和职责边界拆分不同 Controller。
- 不要把无关或弱相关接口全部堆到同一个 Controller。
- 新增接口前先判断是否已有合适 Controller；若没有，再按业务边界新建。
- 为公共接口契约、非显然字段、关键业务语义和重要边界添加简洁注释；名称和类型已经充分表达含义时不机械补充注释。
- 避免空泛、重复代码含义或与实现容易失同步的注释。

## 数据与外部调用

- 不要在循环中调用数据库。
- 不要在循环中调用外部或内部 client。
- 数据库操作包括 mapper/service/repository 的 select、insert、update、delete、save/remove 等。
- 应改为批量查询、批量写入或一次性 client 调用。
- 若确实必须在循环中调用，需要先向用户确认，并说明为什么无法批量化、影响范围和风险。
- 编写跨模块或跨服务能力时，若已有 client 或服务可复用，应优先复用现有能力。
- 不要新写重复 client、重复封装接口或重复建设数据源。
- 如果确实需要新增，应先告知用户新增原因、现有能力不能满足的点以及影响范围。

## 领域数据来源

- 编写涉及外部领域对象展示、详情补全、实时状态或历史数据的代码时，应优先从对应领域的权威服务、已有 client 或配置中心获取。
- 业务模块不要复制外部数据源、保存不必要的展示快照或跨库直连外部领域表。

## 异常处理

- 编写业务代码需要抛异常时，优先使用项目统一异常体系和既有错误码/消息机制。
- 不要随意抛裸 `RuntimeException`、`IllegalArgumentException` 或自造异常体系，除非有明确框架或边界原因。

## 日期时间

- 编写涉及业务日期时间的代码时，应使用项目统一的日期时间类型和数据库字段类型。
- 不要用字符串、纯日期或时间戳随意承载需要精确到时间的业务时间。

## 日志

- 在外部系统边界、批量处理汇总、关键状态变化和异常处记录有诊断价值的日志，不机械添加方法或任务开始/结束日志。
- 日志按需包含业务标识、租户、数量、配置编码、任务名和外部调用目标；禁止记录 Token、Cookie、密码、验证码、完整请求体及其他敏感信息。
- 避免在循环中打印大量逐条日志。
- 批量场景优先记录汇总数量和失败摘要。
